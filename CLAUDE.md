# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

tuimail: a terminal email client for one person's own use: IMAP and POP3 to read, SMTP to send, several accounts, vim keys and arrow keys. Rust, ratatui, tokio, MIT. A sibling of tuigram (`../tuigram`, Telegram), tuimeta (`../tuimeta`) and tuitube (`../tuitube`, YouTube): same security posture, same themes (`themes/`), same `text::clean`, `config.rs` (data folder), `settings.rs` (`save_one`), notifications (`notify.rs`, from tuigram), paste handling and UI helpers (`ui::bordered`, `hint_spans`, `hints_fitting`, `fit`, the `?` popup with a Keys and a Settings tab, from tuitube).

## Running

The data folder holds the user's accounts, a cache of their mail, and (through the keychain) their passwords: don't run the app against it to check a change. Verify with tests that render into ratatui's `TestBackend` (`ui/` tests, `app::tests::app()` gives an app with the demo's mail and no network). `tuimail --demo` (`demo.rs`) runs the real UI on made-up accounts and mail in an in-memory store with `App.demo` set: nothing connects or is sent (sending files the copy in Sent). Use a separate data folder for trying things against a server: `TM_DATA_DIR=$HOME/tm-test cargo run` (a full path; relative paths are refused). `docs/hero.png` is one frame of the demo: `cargo test -- --ignored export_hero_screen` writes `target/hero/screen.json` (each cell's character, colors and style), and `tools/hero.py` draws it as Ghostty would (JetBrains Mono, Nerd Font icons, box lines drawn to the cell edges), as tuitube's.

Tests against a real server are `#[ignore]`d and named `live_*` (`src/live.rs`): they run against GreenMail in Docker (IMAP, POP3 and SMTP over TLS with its own certificate, trusted through an account's `certificate`); the commands are at the top of `live.rs`. `cargo test -- --ignored live` with `TM_LIVE_CERT` set.

## Commands

```sh
cargo build
cargo test                       # offline tests
TM_LIVE_CERT=/tmp/greenmail.pem cargo test -- --ignored live
cargo clippy --all-targets       # keep it warning-free
cargo fmt
cargo run -- --demo
```

## Releasing

As tuitube: `.github/workflows/release.yml` builds six targets on a `v*` tag and makes the GitHub release (archives, `SHA256SUMS`, provenance attestation); `cargo binstall tuimail` takes those archives (`[package.metadata.binstall]`), so the release must be up before `cargo publish`. `ci.yml` runs fmt, clippy (`-D warnings`) and tests on Linux, macOS and Windows. Bump `version`, `cargo build`, tests, clippy, `cargo fmt --check`, `actionlint`; commit and push; `git tag -a vX.Y.Z --cleanup=whitespace -F <notes>`; push the tag; once `SHA256SUMS` is up, `cargo publish` then `cargo clean -p tuimail`.

## Security

Everything in a message is from its sender, and everything a server says is untrusted: subjects, names, addresses, bodies, HTML, file names, folder names, flags, sizes.
- Keywords from the server show as tags only if they read back as one could be typed and are what that tag is written back as (`tags::from_keyword`: letters, digits, `-_.`, none that shows as nothing; none starting with `$` but Thunderbird's `$label1`–`5`), at most `tags::MAX_TAGS` a message (`imap::MAX_KEYWORDS` read), and are checked again when read from the store (`tags::from_stored`).
- Text that is shown, stored, copied or notified goes through `text::clean` / `text::one_line` (capped: `mail::MAX_SUBJECT`, `MAX_NAME`, `MAX_ADDRESSES`) when it's parsed (`mail::summarize`, `mail::parse`), again when read from the store (`store::message_row`), and bodies when laid out (`mail::render_text`, `render_html`). Notifications go through `notify::escape`. Text is cut, padded and wrapped by the columns ratatui draws (`text::cols`, `text::wrap`: a halfwidth sound mark, U+FF9E/U+FF9F, is a column though unicode-width counts none), never by unicode-width, so a name can't push what follows it out of view.
- HTML is laid out by html2text (`mail::render_html`) with nothing fetched: images show as their alt text (`Role::Note`), links are numbered and opened only from the `o` picker, which shows the site (`app::link_host` of the whole URL, ended where browsers end it, `%XX` decoded and letters mapped as IDNA maps them (NFKC, lower case: `%2E` and `․` are dots), its end kept when long, letters outside ASCII as punycode: `app::ascii_label`) and the URL itself, with what the link says beside them (`Body::link_text`), never in their place, and not at all when it looks like an address, and only `http`, `https`, `mailto` (`mail::usable_link`). A `mailto:` link opens tuimail's composer with only its addresses and subject (`app::mailto_draft`); `U`'s web page is shown before it opens (`Confirm::OpenLink`). HTML is capped (`MAX_HTML`). Anything that lays out HTML (the reader, quoting a reply, the list's previews: `App::make_previews`, `mail::preview_of`) runs on a thread with a 256 MB stack (`mail::in_background`, `RENDER_STACK`: html2text recurses through the sender's nesting and overflows 8 MB at ~100k levels), with panics contained (`mail::contained`; the panic hook lets those pass, `mail::panic_is_contained`); never call `mail::plain_text` or `render` on the main thread or a tokio worker. mail-parser alone is safe there: every use goes through `mail::read` or `read_headers` (one parser, `mail::PARSER`, with limits below mail-parser's defaults on depth, parts and encoded nesting; its panics contained, the message then "couldn't be read"; a message with no headers is shown as its text). `.cargo/config.toml` builds mail-parser checking every string it makes (`--cfg mail_parser_checked_str`, not `from_utf8_unchecked`) and encodify, its base64 and quoted-printable, with its portable code (`--cfg encodify_scalar`); they're under `[target.'cfg(all())']`, since cargo drops `build.rustflags` when any target rustflags apply, and RUSTFLAGS replaces them, so `release.yml` passes them too; `build.rs` refuses a build without them and says how to make one (`cargo install` from crates.io doesn't read the file: the README passes them; cargo would hide a warning there, not a failure); `encodify` is required at 1.0.1 or later, the first that honours its flag. `mail::summarize` reads the headers alone (`read_headers`), even of a whole message. mail-parser's own SIMD scanner can't be turned off: `mail::tests::mangle` feeds mangled mail to it and checks every scan against its scalar one (`cargo test --release -- --ignored mangled_mail_at_length` for a long run). tuimail picks the body itself (`mail::bodies`: a version with a file name in an alternative is the body only when it's the only one of its kind) and reads List-Unsubscribe as written, its first 8 KB (`mail::unsubscribe_link`). Every part not shown is listed to save (`mail::attachment_parts`), an invite beside the text too, but a version of the text (plain, HTML, watch-html, AMP) an alternative leaves out unnamed; a forward or draft takes all of them (past the 500 listed too) from the same parse as the message (`mail::parse_with_files`), says how many couldn't be read (`AppEvent::Drafted`'s `lost`), and a draft that lost some keeps the saved one it came from (no `draft_of`). Links are found in one pass (`mail::find_url`), at most `MAX_LINKS` per message, none longer than `MAX_LINK`.
- Threads come from senders' headers: anyone can put a message in a conversation whose Message-ID they know. Every row still shows its sender, and threading never changes what a message is or where it's kept; of copies of one Message-ID in a folder, the first to arrive (lowest UID) is the one replies go under (`threads::arrange_arrived`). Nothing else takes a Message-ID for a message's identity: undo finds moved mail by where the move put it.
- Names are quoted when shown as addresses (`mail::Addr::display`: `"Doe, John" <john@x.y>`) and read back with their quotes and escapes (`compose::parse_addresses`), so a name with commas or addresses in it never becomes more recipients. A name seen in mail never replaces one already known for completion (`Store::remember`): anyone can put any name on any address. Addresses are kept whole or dropped (`mail::MAX_ADDRESS`), never cut. The reader shows the address first (`ui::reader::sender`), every From, and the Reply-To addresses a reply would go to when they differ.
- Protocol commands are built only from checked values: tag keywords (`tags::keyword`, checked to be atoms: `tags::is_atom`, again in `imap::set_keywords`), hosts (`account::valid_host`), addresses (`account::valid_address`: no spaces, control characters, `<>,;`), usernames and passwords without CR/LF/NUL or XOAUTH2's `\x01` (`net::check_login`, from `imap::connect`, `pop3::login`, `smtp::login`), message ids kept only if they can't break a header (`mail::valid_id`), IMAP folder names and strings quoted by async-imap (it rejects CR/LF), search words quoted with `\` and `"` escaped and control characters dropped (`imap::search_criteria`), UID sets built from numbers (`imap::uid_sets`).
- TLS (`net.rs`): rustls with ring; the system's verifier (`rustls-platform-verifier`); an account's `certificate` adds certificates that are trusted as roots and also accepted when the server presents exactly one of them (`net::Pinned`; the handshake's signatures are still checked). `Security::None` connects only to this computer (`account::is_local`, checked in `Account::problem` and again in `net::connect`, `localhost` as 127.0.0.1, the peer checked to be loopback) and, on Linux, only to a listener of this user's (`net::listener_is_ours`). SMTP logs in only if EHLO offers AUTH. After STARTTLS / STLS, anything the server sent along with its answer is refused (`pop3::stls`, `smtp::starttls`) or dropped with the client (IMAP), so it can't be injected before TLS. Every read has a time limit and a size cap (`net::read_line`, `pop3::MAX_*`, `smtp::MAX_*`, `imap::MAX_MESSAGE` checked against the body's real size, `worker::POP_MAX`); IMAP FETCH answers are collected up to a count and size (`imap::collect`, `MAX_FLAGS`), and unasked-for ones dropped (`imap::drain`). A UIDL listing is capped (`pop3::MAX_IDS`) and deduplicated. (async-imap's own buffer for one response isn't capped by tuimail.)
- Signing in (`oauth.rs`): PKCE and a random state; the listener is on both loopback addresses, one port free on both (`oauth::loopback`: never a port another program holds on `[::1]`, where the browser may take `localhost`), serves each connection on its own, takes only a request with our state, answers with a page that loads nothing (`respond`), and stops after `SIGN_IN_FOR`; token answers come over `net.rs`'s TLS, capped (`MAX_RESPONSE`) and timed (`HTTP_TIMEOUT`), and tokens are kept only if printable ASCII under `MAX_TOKEN` (`tokens_from`). The refresh token has its own keychain entry (`secrets::token_key`), never read as a password nor a password as it, kept only after a login with its access token worked (`Credentials::remember(used)`); a refusal forgets only what that login used (`Credentials::refused(used)`); access tokens are in memory only, renewed one at a time without holding the tokens (`refreshing`). Such an account sends only through its provider's servers (`Provider::smtp_hosts`, `Account::problem`).
- Passwords (`secrets.rs`): the system keychain (keyring-core with the macOS, Windows or zbus Secret Service store, called on blocking threads), or typed in tuimail and kept in memory (`Credentials`), or the first line of `password_command`: a full path run without a shell, its output capped, its time limited. It runs once at start with the terminal (so it can ask to be unlocked) and its password is kept; again, without the terminal, only if that failed or after a refusal and `R`; for `auth = "oauth2"`, for each connection (tokens expire). `Secret`'s `Debug` hides it. `password_command` runs in the home folder. A refused password is forgotten (`Credentials::refused`), but not a server that can't let anyone in now (`imap::wrong_password`: UNAVAILABLE, INUSE, SERVERBUG, LIMIT, a NO only; `pop3::busy`: IN-USE, LOGIN-DELAY, SYS; SMTP 4xx); a command's login is held after a refusal until `R` (`Credentials::retry`), and the keychain isn't read again until one is typed (`keychain_refused`: retrying a wrong password every check can lock the account), and the app asks (`PromptKind::Password`); a typed password goes to the keychain only after a login with it worked (`Credentials::remember`).
- Sending (`smtp.rs`): EHLO `[127.0.0.1]` (no hostname in Received headers), Message-ID random at the sender's domain (`compose::new_message_id`), Date in UTC, no User-Agent beyond "tuimail". Bcc is in the envelope only; the copy kept in Sent or Drafts has it (`compose::build`'s `keep_bcc`). Lines are dot-stuffed and made CRLF (`smtp::dot_stuffed`). Sending asks first (`confirm_send`, on by default; always without a subject), listing every recipient (Bcc too) and file, and `y` sends only the draft that was asked about (`Confirm::Send`'s `print`, `Draft::print`); a reply or draft that's ready late never replaces an open composer or confirmation. Attachments are read once, when attached (`compose::Attachment::snapshot`, not through a link or a file swapped in later). MIME boundaries and Message-IDs are random (`compose::random_hex`; no randomness, no send). Once DATA is accepted the send has worked: a failed QUIT is ignored, or the user would send it again.
- Attachments: names made safe (`mail::safe_file_name`: no folders, no control or bidi characters, no leading dots, no Windows device names, extension kept, 120 characters), saved without overwriting (`tools::save_new`, `create_new`, 0600) and marked as from the internet (`tools::mark_downloaded`); opening goes through tuimail's own `opened/` folder, and types not in `tools::SAFE_TO_OPEN` (pictures, sound, video, PDF, plain text) ask first (`Confirm::OpenAttachment`), checked again on the name it was saved as; a file is opened only if it's still the one listed (`App::extract`). Files attached for sending must be full paths of plain files under `compose::MAX_ATTACHMENT`; `\\server\share` paths are refused (`config::maybe_remote`).
- Programs: `PATH` is cut to its absolute folders at start (`tools::absolute_path_entries`); the editor and xdg-open are found as full paths (`tools::on_path`); links and files open with `open` / ShellExecute / xdg-open, never a shell (`tools::open_externally`). The editor gets a 0600 file with a random name in the data folder's `drafts/` (the demo: a private temp folder, `tools::private_temp_dir`), run from there, read back without following links (`tools::read_back`), removed after.
- AI agents: everything an agent sends is untrusted, and so is its name (`agent::shown_client`, cleaned, said as "as it calls itself"). There's no call that deletes for good, sends, opens links or attachments, makes filters or changes settings (`agent::Call`, `deny_unknown_fields`); `move_to_trash` is refused for mail in Trash and for accounts without one (where `d` would delete for good), and moving to Trash or Junk takes their own tools. At most `agent::MAX_IDS` a call, `CHANGES_PER_HOUR` and `TRASH_PER_HOUR`. Moves into Drafts or Sent are refused (what's there is taken as the user's own), and agents see and change only the user's own folders, never another user's, a shared or a public one (`imap::foreign`). Downloads for agents' reads are one per message and limited by the hour (`DOWNLOADS_PER_HOUR`, `DOWNLOAD_BYTES_PER_HOUR`). An agent undoes only agents' changes; the journal names them as agents. Questions show senders by address and folders by their whole name (`App::folder_path`), and wait `AGENT_GRACE` before a key answers them (a key before it answers nothing: they come up on their own). Agents are answered only while the setting is on, re-read from settings.toml for each call (`App::agents_allowed`), so turning them off in another tuimail counts. The socket is in the private data folder (checked with it: `config::make_private_dir`), made 0600, answers only a peer with this user's uid (`peer_cred`), reads one capped line with a time limit, a few at a time, and its connections end with it; `tuimail mcp` asks only a socket of this user's, not through a link, answered by a peer of this user's. Everything from mail reaches agents with links as their site only (`agent::hide_links`, `mail::find_any_url`: subjects, names, previews, text). Unix only for now.
- Pastes: as tuitube, a run of different keys read together is pasted text, never commands (`App::on_terminal_events`); a confirmation ignores `y` for `CONFIRM_GRACE`.
- Files: the data folder is made 0700 and checked, with what's in it, to be this user's alone (`config::make_private_dir`); `settings.toml` and `accounts.toml` are written 0600 through a rename (`settings::write_private`); they and an account's `certificate` are read only if they're plain files under 1 MB, through one open file (`config::read_capped`); the store is opened without following a link (`SQLITE_OPEN_NOFOLLOW`). The store has `secure_delete` on and checkpoints after removals (`Store::scrub`).

## Architecture

**Event loop (`app.rs`, `App::run`).** One `tokio::select!` over terminal events, `AppEvent`s and a 250 ms tick, as tuitube's. All state is in `App`; only it writes the store. The tick expires the status line, shows the message under a resting cursor beside the list (`PREVIEW_AFTER`) and marks it read once shown (`PREVIEW_READ_AFTER`; `Enter` marks at once), sends due notifications, and runs each account's check every `check_minutes`.

**Workers (`worker.rs`).** One task per account (`worker::spawn`), holding its connection and running `Request`s in order; it never touches the store, and reports `Event`s, which reach the app as `AppEvent::Worker` by the account's id. Requests waiting together are batched (`worker::batch`): repeats of a check run once, last, so a flag set meanwhile is stored before it's read back. While the connection is down, reads fail at once (for `OFFLINE_FOR` after a failure) but changes (`Request::changes`: flags, moves, deletes, appends with `retry`) are held, in order, and made once it's back (tried every `RETRY_EVERY`), before anything newer (after a check reconnects too); a change the server refuses (`imap::Said`), or one that broke the connection `MAX_TRIES` times, is reported. Appends carry an id answered by `Event::Appended`: a draft's composer waits for it (`Composer.saving`, `App.appends`), and the draft it replaces is deleted only then. A folder an append needs (Sent, Drafts) is made. Folder roles come from the account's settings, then SPECIAL-USE, then a usual name at the top or right under INBOX or [Gmail] (`imap::role_of`), never from another user's or a shared namespace (`imap::other_namespace`), one folder per role (`imap::dedupe_roles`). IMAP accounts whose server has IDLE get a second connection on the inbox (`watch_inbox`), which reports `Event::Changed`. Sending (`worker::send`) runs as its own task with the account's `Credentials`.

**Sync (`worker::sync`, `App::on_synced`).** The store keeps, per folder, UIDVALIDITY and a UID range `low..=high` of which every message is cached (`store::Known`). A check SELECTs the folder; a new UIDVALIDITY (or more new mail than `fetch_count`) resets the folder's cache; new mail is `UID SEARCH UID high+1:*` (the first time, the newest `fetch_count` by sequence number); flags are fetched for `low..=high`, and cached UIDs missing from the answer were deleted elsewhere; UIDs in it the cache lacks (a move the server refused) are fetched again (`Request::Headers`), unless moved here in the last `LOCAL_FLAGS_WIN` (`App.local_removed`). Flags changed here in that time keep their local value. Messages marked `\Deleted` count as gone. Every request by UID carries the UIDVALIDITY it was made under and is refused under another (`worker::select_same`); so do confirmations, the move-to picker, and what a composer keeps (`app::Kept`: account id, folder, UID, UIDVALIDITY; `App::resolve`). Deletes for good are stored until the server has made them (`Store::add_pending_deletes`) and made again at start (`App::redo_deletes`); quitting with changes still held asks (`Confirm::Quit`). Without UIDPLUS, a plain EXPUNGE is sent only if every message marked deleted is one tuimail marked (`imap::expunge`). A new UIDVALIDITY closes the reader and drops marks and pending replies on that folder. Scrolling near the end asks for older mail (`Request::Older`) below `low`. Search results from the server are stored like any header.

**POP3 (`worker::pop_check`, `App::on_popped`).** One check at a time (`AccountState.pop_again` queues the next); ids already in `pop_seen` are never stored twice. A check downloads ids not seen before (`store` table `pop_seen`, which keeps every id ever downloaded or skipped, written before a message is parsed), newest first, at most `POP_BATCH` and `POP_BYTES`; the first check takes only the newest `fetch_count` (first by `pop_checked`, not by `pop_seen`, which empties with the server). A message over `POP_MAX` is read to its end and skipped (`pop3::TooBig`), so the session stays in step; one with a line too long ends the session and is skipped for good (`pop3::BadMessage`). Local folders keep every body whatever its size (`Store::add_local`), and `Store::move_local` removes only what it copied. Deleting from tuimail's Trash marks the id (`Store::mark_pop_removal`); the next check DELEs it, and it's gone once QUIT is answered. With `leave_on_server = false`, mail is marked for removal once it's stored, never before. A POP3 account's folders are local (`app::local_folders`): its mail moves between them in the store (`Store::move_local`).

**Store (`store.rs`).** SQLite `tuimail.db`: `folders` (role, counts, the sync state), `messages` (summary and flags with the tags, keyed by account, folder and UID; POP3 and local folders number their own, never giving a UID twice: `local_uids`; `Store::migrate` adds columns to older caches), `bodies` (raw messages under `MAX_KEPT_BODY`), `pop_seen` (written in one transaction per listing, `Store::pop_skip_all`), `pop_checked` (accounts checked before), `addresses` (for completing To/Cc/Bcc, `Store::complete`), `pending_deletes`, `changes` and `changed`.

**Tags (`tags.rs`).** IMAP keywords spelled as Thunderbird spells them (lower case, modified UTF-7, its `$label1`–`5` by name), read with the flags (`imap::flags_of`) and kept in `Flags.tags`. `t` (`App::pick_tag`) puts one on or takes it off (`App::tag`): here at once, like a flag (`App::change_here`, `local_flags`), then `Request::Tag`, which is refused when the folder can't keep new keywords (`imap::Selected::keeps`). POP3 accounts' tags are only in the store. `tag:work` in a search is `KEYWORD` on the server (`imap::search_criteria`) and a match on the column here (`Store::search`).

**Changes and undo.** Each key's change to mail (read, star, tag, move: archive, junk, Trash) is one `store::Change`, a row in `changes` with a `changed` row per message (account, folder, UIDVALIDITY, UID, Message-ID, whether it had the flag or tag, where it was moved, its UID there in folders kept here, and on the server that folder's UIDVALIDITY and UIDNEXT just before the move, `Event::Moved`), gathered while the key is handled (`App::note_change`) and kept after it (`App::on_key` → `keep_change`); 30 days, at most 1000 (`store::KEEP_CHANGES_FOR`, `MAX_CHANGES`), dropped with the account. No subjects or names: they're looked up in the cache to show. `z` undoes the newest (`App::undo_last`), `Z` lists them (`App::pick_change`). Undoing sets back only the messages the change changed (`Changed.had`), under the same UIDVALIDITY, and moves back exactly those it moved (`App::move_back`): in folders kept here by the UID the move gave them, if the message there is still theirs; on the server from where the move put them (`Request::MoveBack` under that UIDVALIDITY, `imap::find_moved`: from UIDNEXT on, one per moved message by its whole Message-ID and size), taken off the list once the server says which (`Event::MovedBack`); a move the server hasn't made yet isn't undone. Old changes are dropped at start and not shown (`Store::prune_changes`), and deletes for good forget their Message-IDs (`Store::forget_changed`). Reading, a reply's `\Answered` and deletes for good aren't changes.

**AI agents (`agent.rs`, `mcp.rs`).** `tuimail mcp [--demo]` is an MCP server on stdio (rmcp, `#[tool_router]`, `mcp::INSTRUCTIONS` under Claude Code's 2,048 characters) holding nothing: each tool is an `agent::Call` sent as one JSON line to the running tuimail over `agent.sock` in the data folder (`demo-agent.sock` for the demo), listened on only while the `agents` setting is on (`App::listen_for_agents`), and reaching the app as `AppEvent::Agent` with a oneshot reply (`App::on_agent`). Reads answer from the cache (`agent_search`, `agent_read`: the text from `mail::plain_text` on a big-stack thread, links as `[link: host]`, `agent::hide_links`; a body not cached is downloaded, `agent_reads`). Changes are checked (`App::agent_plan`: ids still meaning their message, `agent_key`; where to; the rules; the hourly limits, `agent_spent`), then, with `confirm_agents` (the default), wait for `y` (`Confirm::Agent`, `agent_asks`, re-checked when answered, refused after `agent::ASK_FOR`), and are made through the user's own paths (`change_flag`, `change_tag`, `move_messages`) as one change whose `who` is the agent (`agent_apply`). Message ids for agents are `agent::handle`s (account, folder, UIDVALIDITY, UID).

**Conversations (`threads.rs`).** With `threads` on (the default) and no search, `App::reload` puts the list in conversations (`threads::arrange`): each message under the nearest message it names that's listed (In-Reply-To, then References from the latest), never under one that answers it (`answers`, walking up at most `MAX_CHAIN`), a Message-ID's first message only; the conversation with the newest message first, each oldest first, depth first. `Item.thread` carries the lines (`tree`, drawn at most `MAX_DEPTH` deep) and whether a reply's subject is its parent's (`base_subject`: then the list shows its text instead). Done from the cache's headers, the same for IMAP, POP3 and All inboxes.

**Signing in (`oauth.rs`).** `auth = "oauth2"` without a `password_command` signs in here (`oauth::built_in`), with Microsoft or Google by the servers (`provider_for`) as the account's app or tuimail's (`client_for`: `oauth_client_id` / `oauth_client_secret`, else `MICROSOFT_CLIENT_ID`, `GOOGLE_CLIENT_*`, empty until registered). `SignIn::start` listens on the loopback (v4 and v6, one port) and makes the provider's link (PKCE S256, a random state, `login_hint`); the app opens it (`AppEvent::SignInOpened`, `tools::open_externally`, the link copied too; never in the demo) and `finish` waits for the browser's return (`callback`: our state only, `SIGN_IN_FOR`) and trades the code for tokens (`token_request`: HTTP/1.1 POST over `net::connect`, `parse_response`, `tokens_from`). `Credentials` keeps the tokens (`set_tokens`): the access token while it lasts, then a refresh (`access_token`, one at a time), the refresh token from memory or the keychain; `invalid_grant` is `SignInAgain` → `NeedPassword`, and `P` signs in again (`App::sign_in`). The add-account form signs in when no password is typed and there's an app to sign in as (`Setup::account`), then checks the login with the token.

**Reading (`mail.rs`).** `mail::summarize` sums up headers for the list; `mail::parse` gives text and HTML parts, attachments, Reply-To, List-Unsubscribe; `mail::render` lays one out for the reader's width (`Body`: lines of `Seg`s with a `Role`, and the links), in the background (`App::render`), again when the width changes (`App::after_draw`).

**Writing (`compose.rs`, `composer.rs`).** `compose::Draft` is plain data; `compose::reply`, `forward` and `from_saved` make one from a message (in the background, `App::draft_from`, since quoting HTML lays it out); `compose::build` makes the MIME message with mail-builder. `composer::Composer` holds the fields as ratatui-textarea inputs and returns an `Action` for each key. A sent message goes to Sent (IMAP APPEND, the folder made if there's none; POP3 in the store); a draft is APPENDed to Drafts and closes the composer; editing a saved draft deletes it once the new one is sent or saved.

**UI (`ui/`).** `mod.rs` lays out the sidebar, the list and the reader (the reader beside the list from `WIDE` columns, in its place below, one pane below `NARROW`), the status bar (hints with keys in backticks, the account's state on the right), and the popups: prompt (search, password, attach), picker (move to, links, attachments), confirm, help. `sidebar.rs` (every inbox, accounts, folders by role then nested by name: `app::folder_rows`), `list.rs`, `reader.rs`, `composer.rs`, `setup.rs` (the add-account form, `setup::Setup`, which fills servers from `account::preset` / `account::guess` and checks the login, `app::check_login`, before saving).
